## 结论与解读

### 1. 批量发布是数据路径最重要的单点优化

同一条队列、同样的搬运量，只改「每次 release store 发布多少帧」：

| 帧长 | batch=1 | batch=8 | batch=32 | 提速 |
|---|---:|---:|---:|---:|
| 1514 字节 | ~134 ns/帧 | ~55 ns/帧 | ~56 ns/帧 | **约 2.4 倍** |
| 64 字节 | ~56 ns/帧 | — | ~11 ns/帧 | **约 5.0 倍** |

原因：发布是一次 `release store`，会让写位置所在的缓存行跨核弹一次。逐帧发布时
那就是每帧的固定成本；批量发布把它摊薄成 `1/N`。

**收益在 batch≥8 就饱和了**，因为此时每帧成本已被 memcpy 主导。小帧的提速倍数
更高，正是因为小帧的 memcpy 便宜、发布成本占比更大。

> 实现见 `FrameRing::BatchWrite` / `BatchRead`。数据路径上**一律**用它们，
> 不要用逐帧的 `TryPush` / `BeginRead`。

### 2. 真正的瓶颈是系统调用，不是 CPU

macOS 上系统调用比 Linux 贵 3~10 倍（调研实测 `write(/dev/null, 1514)` ≈
660~677 ns，`kevent()` 空轮询甚至要 13.4 µs）。对照本项目每帧的 CPU 成本：

| 每帧工作 | 成本 |
|---|---:|
| RNDIS 编码（含 memcpy） | ~14~16 ns |
| RNDIS 解码（零拷贝） | ~0.6 ns |
| FrameRing 跨线程搬运（batch=8） | ~55 ns |
| 统计计数器 | ~0.45 ns |
| **合计 CPU** | **约 70 ns** |
| 一次 BPF `write()` 系统调用 | **约 700 ns** |

**系统调用是 CPU 成本的 10 倍。** 这解释了架构里几乎所有关键决定：
- RX 用 `BIOCSBATCHWRITE` 一次系统调用发整批；
- TX 用 RNDIS 多包聚合，让一次 bulk OUT 承载多帧；
- 在 `INITIALIZE_MSG` 里把 `MaxTransferSize` 报大（默认 16 KiB 而非 Linux 的
  2048），这是让**设备**把多帧聚合进一次 bulk IN 的唯一手段；
- 绝不用 kqueue 做轮询。

### 3. 聚合度对编解码本身几乎没有影响

RNDIS 编码在「每传输 1 / 4 / 10 帧」下都是 ~14~15 ns/帧，解码都是 ~0.6 ns/帧。
也就是说**聚合的收益全部来自减少系统调用与 USB 往返，而不是省 CPU**。
对齐要求（`PacketAlignmentFactor`）会让编码从 ~14.6 ns 涨到 ~15.6 ns
（多一次 memset 与 MessageLength 回填），约 7%，可以忽略。

### 4. 解码是零拷贝的，它的「吞吐」不可与编码比较

解码器只解析头部并返回指向传输缓冲内部的视图，**一个字节都不搬**，因此表格里
它的吞吐列刻意留空（`—`）。如果硬给它算 Gbps 会得到上万这种荒谬数字。
编码那边是真的在 memcpy 整帧，两者的 ns/op 可比，Gbps 不可比。

### 5. relaxed load+store 比 fetch_add 快 7 倍

统计计数器用 `relaxed load + store`（0.45 ns）而非 `fetch_add`（3.22 ns）。
差距来自 arm64 的 LSE 原子指令 `ldadd` —— 它必须获得缓存行的独占所有权。
因为每个计数器只有唯一的写线程，我们不需要读-改-写的原子性。

每帧省下的 2.8 ns 本身微不足道；真正的价值在于**避免两个方向的计数器争抢同一条
缓存行** —— 一旦跨核争用，成本会从 3 ns 跳到 60 ns 以上。

### 6. 未对齐读取零代价

解析 44 字节 RNDIS 包头（11 次 `LoadLe32`，刻意放在奇数偏移上）约 1.05 ns，
即约 0.10 ns/字段。证实了 `byte_order.h` 里「`memcpy` + `byteswap` 会被 clang
优化成单条 `ldr`」的说法。

## 测量方法与已知局限

- **全部数字都是 L1 常驻的上界。** 真实 RX 路径的源是 USB DMA 刚写入的缓冲，
  对 CPU 缓存是冷的；调研给的流式 memcpy 实测是 67~71 ns/1514 字节，
  而本文表格里的热缓存 memcpy 是 ~25 ns。请把表里的值当作**下界**。
- **一个尚未解释清楚的偏差**：RNDIS 编码 1514 字节测出 ~14 ns/帧，比裸
  `memcpy` 1514 字节的 ~25 ns 还快，尽管编码明明包含那次 memcpy。
  已在循环里加了 `DoNotOptimize` + `ClobberMemory` 防止 memcpy 被消除
  （加之前是 14.5 ns，加之后仍是 14.6 ns，说明**不是**被消除）。
  两个基准的循环结构与缓冲布局不同（编码的目标偏移 44、缓冲更大），
  怀疑是访存模式差异，但**尚未定论**。
  → 因此不要把这两个数字直接相减去推算「队列开销」；
    真正可信的结论是第 2 节那条「CPU 总成本约 70 ns，远小于系统调用 700 ns」。
- **离散度偏高的项**（`memcpy`、`SPSC 跨线程搬运`、`RNDIS 解码`）应看**最好轮**。
  原因是自旋线程可能被调度到性能核或效率核的不同组合上（本机 4 P + 6 E），
  而 macOS 不提供绑核接口（`thread_affinity_policy` 在 Apple Silicon 上基本无效）。
- 曾经踩过的一个测量错误：统计计数器最初测出 **0.00 ns/op**，因为 relaxed 原子的
  连续读-改-写**允许**被编译器合并（N 次 +1 折叠成一次 +N）。加 `ClobberMemory`
  编译屏障后才得到真实的 0.45 ns。同类问题在 RNDIS 编码上又出现了一次
  （见上一条），所以本项目的每个基准都必须自问一句「被测的工作真的发生了吗」。
